### 2026-09-10 (continuation session — AgentStateMachine concurrency safety, closing the item every entry since the MacroScheduler slice flagged)

- **AgentStateMachine concurrency safety (named as a "known limitation" since the 2026-09-09 MacroScheduler entry, and repeated as an open next-candidate in every entry since):** `state` is now `@Volatile` and `transition()`'s check-then-set is wrapped in `synchronized(lock)`, matching the `@Volatile var` + `synchronized(lock)` idiom already used in `DroidCommandSession`. This closes a real memory-visibility gap, not a cosmetic one: reading a plain `var` from a different thread than the one that last wrote it has no happens-before guarantee under the JVM memory model, and `MacroScheduler` already introduces exactly that cross-thread pattern (its own background scheduler thread calling `transition` while another thread may be reading `.state`).
- **What this does and does not fix, stated plainly rather than oversold:** it guarantees (a) a `transition` on one thread is visible to a `.state` read on another, and (b) two concurrent `transition` calls can never both pass the terminal-state check before either writes — so a race can no longer let two callers both believe they legitimately transitioned out of a non-terminal state, or leave a reader observing a stale value indefinitely. It does **not** make it correct for two unrelated logical tasks (e.g. a live Pilot instruction and a scheduled macro) to share one `AgentStateMachine` instance — their transitions would still interleave into a single, meaningless sequence even though no individual read or write is corrupted anymore. `MacroScheduler`'s own doc comment (updated alongside this change) still correctly recommends a dedicated instance per independent task; this fix only guarantees that whichever single task owns an instance at a given time observes it correctly across threads.
- Unit-tested (`AgentStateMachineTest`, two new tests added alongside the existing four single-threaded ones): a transition submitted on a single-thread executor is visible via `.state` on the test thread after `.get()` (proves cross-thread visibility, not just single-threaded correctness); 16 threads racing via a `CountDownLatch`-gated simultaneous start all call `transition` to the same terminal state, asserting exactly 1 success and 15 `IllegalAgentTransition` rejections (proves the check-then-set race is closed under real concurrency, not just by inspection).
- Updated `MacroScheduler.kt`'s own doc comment and `docs/ARCHITECTURE.md`'s MacroScheduler row: both previously said `AgentStateMachine` had no locking of its own and recommended a workaround "until/unless" it became concurrency-safe — now factually updated to say it is concurrency-safe for cross-thread visibility/atomicity, while preserving the still-true recommendation to use a dedicated instance per independent task (the semantic-conflation risk, not a data race, is what remains).

- Shipped in `core-security`: `JsonFileGrantStore.kt` and `JsonFileAuditLog.kt`, extending the exact `JsonFileMacroStore`/`JsonFileConversationStore`/`JsonFileKnowledgeStore` pattern (id-allow-list + normalize-then-`startsWith` path-escape defense, `kotlinx.serialization` DTOs, `core-security`'s first two dependencies added: the `kotlin.plugin.serialization` plugin and `kotlinx-serialization-json` 1.7.3, matching every other module's pin).
- **A real design difference from the three prior stores, not a copy-paste:** `Grant`/`AuditEvent` aren't immutable data a caller just saves and loads — `GrantStore.consume`/`revoke` mutate lifecycle state, and persistence would be security theater if that mutation didn't survive a restart too (a revoked grant reverting to live, or a single-use grant becoming reusable again, the moment the process restarts). `JsonFileGrantStore` stores `consumed`/`revoked` as fields on the same record file and treats `consume`/`revoke` as read-modify-write operations, rather than the separate in-memory sets `InMemoryGrantStore` uses. `JsonFileAuditLog` is deliberately append-only (JSON-Lines, one line per event, no delete/rewrite path at all) since an audit trail's entire purpose is proving a privileged action happened even after the process that ran it is gone — unlike the three prior stores, there was never a "delete" method to mirror.
- Both fail closed at capacity the same way their in-memory counterparts do, but by counting real state on disk fresh on every call (existing grant files; the log file's line count) rather than an in-process counter — the same "genuinely re-read from disk, never just cached" discipline `JsonFileKnowledgeStore` already documents, and the only way capacity stays correct if more than one store instance (or process) touches the same directory/file.
- Unit-tested (`JsonFileGrantStoreTest`/`JsonFileAuditLogTest`): every existing `InMemoryGrantStore`/`InMemoryAuditLog` test case reproduced against the file-backed version (unknown/null id denial, capability mismatch, single-use consumption, multi-use survival, revocation, expiry, capacity fail-closed), plus new tests specific to persistence: revocation and single-use consumption both survive a fresh store instance over the same directory, `../`-shaped and absolute-path-shaped grant ids rejected, `consume`/`revoke` are no-ops for an unknown id, audit events round-trip with exact type/subject/detail/timestamp preserved, events survive a fresh log instance over the same file in original order, and capacity enforcement stays correct across two separate `JsonFileAuditLog` instances over the same file (proving the fresh-recount design, not just asserting it).

This slice achieves the same end — callers going through `ExecutionTarget` never see `ProcessBuilderShellExecutor` directly — via a new, real `LocalProcessExecutionTarget` that composes the existing, **unmodified** `ShellExecutor` interface. `core-shell` is not touched at all, confirmed directly via `git diff --stat`, not merely argued.
- **`ExecutionTarget`/`ExecutionContext`/`ExecutionResult` are verbatim from the spec**, with the same not-`suspend` deviation every `suspend fun` in this codebase has taken since P0.1 (still zero coroutines dependency anywhere in this repository, reconfirmed directly rather than assumed from memory). `ExecutionTarget.type`/`availableCapabilities` reuse `core-agent`'s existing P1.0 `ExecutionTargetType`/`CapabilityId` types rather than redeclaring them.
- **`PrivilegeLevel` (`USER`/`ELEVATED`/`ROOT`) coincidentally shares a name with the pre-existing `core-root.PrivilegeLevel` (`NONE`/`USER`/`ROOT`) — a real naming proximity, checked and deliberately not reconciled with it, unlike the P1.0/P1.1 `CapabilityRegistry` situation.** The two live in different packages (`ai.droidcommand.execution` vs `ai.droidcommand.root`) with different value sets and different purposes (root-mechanism state vs. execution-context privilege), and neither module depends on the other in either direction — there is no real ambiguity here to resolve by renaming, only a coincidental name reused for a genuinely different concept, per the spec's own verbatim naming. Stated explicitly here so a future session doesn't mistake this for an unresolved collision the way the earlier `CapabilityRegistry` one genuinely was.
- **`LocalProcessExecutionTarget.isHealthy()` is always `true`** — spawning a subprocess is a plain JVM capability present in any environment this repository's own tooling already assumes, the same claim `core-shell.ShellExecutor`'s own doc comment makes; not a fabrication, a real fact about this environment. `execute()` maps a real `ShellExecutionResult.Success`/`Failure` onto `ExecutionResult`, with **two honest, stated simplifications, not silently smoothed over:** (1) `timedOut` is always `false` — today's `ShellExecutionResult` sealed class folds a real timeout into `Failure.reason`'s free text rather than a distinct case, and string-matching that text for "timed out" would be a fragile, undocumented coupling to `ProcessBuilderShellExecutor`'s exact wording; the timeout is still real and still produces `exitCode = -1` with the reason in `stderr`, just not distinguished via this flag. (2) `verified` is always `false` — real result verification is explicitly P1.4's `ExecutionRouter.verifyResult` job, not attempted here; claiming `true` would be exactly the kind of fabricated success `core-security.AgentRouterGateway`'s own row already refused for `ExecutionResponse.Success`.
- **`NullExecutionTarget` is the honest stand-in for the other 6 target types** — a single class parametrized by `ExecutionTargetType` rather than six near-duplicate classes, mirroring `core-root.NullRootProvider`/`NullRootExecutor`'s already-established "self-documented non-real implementation" precedent. This environment has no Android device, Termux, Docker socket, SSH-reachable remote host, or Proxmox API to back `ANDROID`/`TERMUX`/`DOCKER`/`REMOTE_HOST`/`PROXMOX_VM`/`PROXMOX_LXC` with anything real; `isHealthy()` always `false`, `execute()` never spawns anything and always reports a clearly-labeled unavailable result — an honest signal, never a fabricated success, and never leaving the gap silently undocumented in code the way this project's own rules forbid.
